# 模板设计原则（Design Principles）

> 本模板在一轮轮"为什么新工程里有这么多多余的东西"的质疑中收敛出的八条原则——每一条都对应一次真实踩坑。机制细节见 [assembly.md](assembly.md)（怎么工作）与 [bootstrap.md](workflow/bootstrap.md)（怎么用）；本文只记录取舍的**理由**。最后更新：2026-09-12

## 1. 模板是参考库，不是拷贝源

模板的价值分三类：**契约知识**（envelope、分层公理——永远只被参考）、**已测试的组件**（机制、能力——按需继承）、**模板身份**（README/CHANGELOG/LICENSE/docs——永远不拷贝）。

反例：早期装配把模板身份文件与知识库全部随工程走，新工程带着模板的 README、CHANGELOG 和 17 篇文档出生——这些描述的是模板，不是你的服务。修正后身份文件由 Agent **生成**，知识库留在模板目录按需查阅。

## 2. 正向清单优于负向清单

"复制全部 → 裁剪"是负向清单：生成物带全套行李，且删除比组装难（删除面清单、守护测试都是为"删"而生的机制）。装配反转为正向清单：**未选的组件根本不存在**，从源头消灭删除步骤。

## 3. 已测试的代码继承，未测试的代码生成

重写 envelope、中间件这类契约代码 = 把 266 个测试踩过的坑重新踩一遍，且 100 个工程会漂移出 100 种实现，契约统一性消失。因此**机制与能力组件拷贝已测试的实现（测试随代码走）**；"参考-生成"只用于两类东西：身份文件（本就是新工程的）与业务代码（add-capability 流程）。这是模板与教程的分界：教程给知识让人重写，模板给知识 + 已测试的实现让人继承。

## 4. 契约内核最小化：不可选的只有契约本身

"最小 web 服务"的最小集由契约决定，不由习惯决定：app 工厂 + envelope + 健康探针 + X-Request-ID。反例：中间件套件（metrics/auth/限流/日志）曾捆绑进"最小装配"——用户只想要 FastAPI + health，却收到整车配件。修正后中间件全部成为 opt-in 机制。

## 5. 机制逐个确认（先检查、再确认）

横切机制不是越多越好：logger 与 web 服务本体无关，鉴权限流是运维决策。初始化时 Agent 逐个问"需要 metrics 吗？鉴权？限流？日志？"，明确要的才进装配——默认一个都不要。envelope 与 request_id 是契约本身，不受此约束。

## 6. 生成优于拷贝的东西：身份文件、依赖清单

身份文件（README/CLAUDE.md）写的是新工程，不是模板——生成。依赖清单按**所选组件的声明合并生成**（组件自带 requirements 声明，像包管理器一样确定性、带版本约束），而不是拷贝模板的整份 requirements；业务代码新引入的依赖由 Agent 开发完成后扫描 imports 补充。

## 7. 每层只说一次

同一句话在 hero/About/正文各出现一遍，每遍都不新增信息——这是文档腐化的起点。分层纪律：hero 说"有什么"，About 说"为什么这样设计 + 怎么用"，正文/docs 说"具体是什么"；README 指路，docs 承载细节；使用流程看 bootstrap，机制原理看 assembly，取舍理由看本文。

## 8. 可执行契约优于散文约定

红线写成测试（架构方向、双注册、足迹检查、装配清单），随工程发布为 CI 反馈；散文约定只写进文档的，终将无人执行。反例：双注册约束在文档缺失时曾退化为一句话提醒，机器守门随之失守——宁可测试优雅跳过，不可约定只剩散文。
